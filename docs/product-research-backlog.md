## R1 · 主代理分流插件：在原工作入口自然省 token

**状态：待决策。** [Notion 对应卡](https://app.notion.com/p/3db3285284df81b9ae61e6c37df04039)

**面向谁：** 已有主代理和多个 AI 订阅的个人开发者。

**问题：** 用户是否愿意保留 Codex 等原入口，只让合适的小批次自然走下游？

**假设或依据：** 减少打包、切换和验收操作，比展示更多平台更有价值；目前只是待验证假设。

最小研究或实验：

- [ ] 列出 10 个真实可描述的开发辅助场景，区分本地脚本、主代理、可外派批次。材料使用公开或合成样本。
- [ ] 对照现有 task-tiering、CLI 请求和主代理原生能力，标出需要用户操作的步骤、重复能力和缺口。
- [ ] 设计 3 个最小任务包及验收卡，用干运行记录打包与验收步骤；真实下游实验须先完成 E0。

**交付与验收：** 一页入口流程对比、10 个场景清单、3 个可执行任务包草案，以及继续/停止建议。 每条结论带来源/日期或实验记录，说明反证与限制。

**停止条件：** 如果外派的打包和验收负担高于原入口直做，缩小批次范围，不为提高外派比例强行路由。

**白天拍板：** 要不要把“主代理默认分流”作为产品主入口？

## R2 · 闲置额度管家：多 CLI 的可用性与优先顺序

**状态：待决策。** [Notion 对应卡](https://app.notion.com/p/3db3285284df8142a109f96c2bd10648)

**面向谁：** 同时持有多个客户端套餐、希望使用闲置额度的个人用户。

**问题：** 现有订阅和赠送积分，能否在正常授权下稳定用于可验收任务？

**假设或依据：** 真实可调用状态、额度到期和合格交付成本，比静态平台名单更能指导选择。

最小研究或实验：

- [ ] 先核实 WorkBuddy 与 TeleAgent 的官方执行入口、正常授权方式、结果/取消能力与限制；未确认的字段留空。
- [ ] 为一个备选官方兼容 API 建立同样的能力表，明确它的费用与客户端赠送积分是否同一权益；不新增付费调用。
- [ ] 设计只读资格筛选与排序例子：额度未知、赠送积分到期、登录失效、质量不足。记录来源及日期。

**交付与验收：** 最多 3 个候选的能力/权益表、6 个选择情境、第二执行器接入建议及被排除原因。 每条结论带来源/日期或实验记录，说明反证与限制。

**停止条件：** 无受支持调用入口、权益不清或需要提取凭证时停止该候选。不能把可使用命令行工具当作提供外部 CLI。

**白天拍板：** 第二个平台先验证 TeleAgent、已有官方 API，还是先保持单平台？

## R3 · 批量任务工作台：先做好反馈分类与字段提取

**状态：待决策。** [Notion 对应卡](https://app.notion.com/p/3db3285284df813baee5ce23d8eb71b9)

**面向谁：** 产品、运营和需要处理重复文本工作的个人用户。

**问题：** 不写代码的用户，是否更需要上传一批材料、拿到可检查结果的独立入口？

**假设或依据：** 明确的任务模板、来源证据和结果导出，可能比通用聊天更容易形成稳定使用。

最小研究或实验：

- [ ] 制作反馈分类、字段提取两个模板，每个准备 10 条合成样本和独立验收标准。
- [ ] 画一条最短操作流程：选模板、提供材料、检查结果、导出；列出空输入、缺字段、错证据、重复提交场景。
- [ ] 用静态样例或干运行比较现有工作台与模板方案，不提前扩展复杂文档、自动编辑代码或登录网页。

**交付与验收：** 两套样本/验收卡、一页流程或原型、异常场景表，以及最先上线的一个模板建议。 每条结论带来源/日期或实验记录，说明反证与限制。

**停止条件：** 如果模板间规则差异过大或验收依赖开放式判断，缩窄输入范围，不承诺通用自动完成。

**白天拍板：** 首个稳定场景选反馈分类还是字段提取？是否值得保留独立工作台？

## R4 · 节省验证工具：用完整成本证明分流值得

**状态：待决策。** [Notion 对应卡](https://app.notion.com/p/3db3285284df812691d5caab17da6f94)

**面向谁：** 希望核算 AI 工作流收益的个人开发者和小团队。

**问题：** 能否准确回答用了多少下游、哪些任务值得分流，而不把次数当 token 节省？

**假设或依据：** 能解释完整交付成本和失败返工的记录，是路由决策的必要证据；当前还没有完整分母。

最小研究或实验：

- [ ] 基于已有 3 次合成批次设计最小台账，分开业务/测试/探针/尝试以及主代理/脚本/下游。
- [ ] 做 6 个手算样例：下游通过、主代理回退、重试、失败、未完成、未知用量，验证分子分母一致。
- [ ] 定义同任务同验收的直做基线，列出目前缺失的主代理打包、验收与返工用量；不凭空补数。

**交付与验收：** 最小台账草案、6 个可复核计算例子、一页看板草图和真实基线实验方案。 每条结论带来源/日期或实验记录，说明反证与限制。

**停止条件：** 主代理用量或对照基线缺失时只报告范围与已知次数；不同平台 token、credit、金额不直接合计。

**白天拍板：** 先做任务比例可见，还是投入可比较成本实验？哪些指标值得进入首页？

## R5 · 夜间执行队列：白天定方向，晚上交付一个结果

**状态：待决策。** [Notion 对应卡](https://app.notion.com/p/3db3285284df813bbe47c2638d531729)

**面向谁：** 白天时间少、已有明确项目和验收标准的独立开发者。

**问题：** 用户能否只做少量方向决策，让已批准的小任务在夜间有边界地完成？

**假设或依据：** 一条选定任务、明确停止条件和次日证据，比无限自主循环更容易使用。

最小研究或实验：

- [ ] 对照当前 Codex 定时跟进、已有 autopilot 和 Task Router 能力，区分可以复用的机制与产品还缺的部分。
- [ ] 设计 5 个干运行情境：未选择、唯一已选、同时多选、重复唤醒、预算/时间到达。
- [ ] 设计一页白天决策与次日交付样例，验证任务不会被自动选中、重复执行或失败后扩范围。

**交付与验收：** 能力复用表、5 个流程演练结果、最小夜班任务契约与次日简报样例。 每条结论带来源/日期或实验记录，说明反证与限制。

**停止条件：** 没有明确已选任务或验收标准就等待；未验证外部任务停止时不得换路重跑。

**白天拍板：** 夜班应成为本项目的主要使用方式，还是只作为现有 Codex 工作流的辅助？

## 交付模板

每张卡交付一页主体结论，证据附后：

1. 本轮问题与范围。
2. 已核实事实、来源链接及采集日期。
3. 最小实验、输入范围、结果与失败例子；没运行就明确标记。
4. 支持与反对该方向的证据、未知项。
5. 继续 / 缩小 / 暂缓建议，以及下一条需要白天决定的问题。

不预填成功率、节省百分比或用户偏好。对外访谈/联系他人需另有明确授权，先使用公开材料、已有记录和合成样本。
