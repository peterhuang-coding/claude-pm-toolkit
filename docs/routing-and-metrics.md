# 分流统计、执行顺序与兜底

本文记录 2026-09-12 确定的演进方向。**当前只有 WorkBuddy 可执行；完整分流统计、多个 CLI 的自动排序与跨平台回退尚未实现。** 不需要为任务分级再调用一个模型，由主代理判断是否值得打包和验收。

## 先把统计分母补齐

目前下游任务有结果和验收记录，但主代理直接完成、本地脚本完成的工作没有统一登记。数据库里的旧路由占位也不等于实际执行。因此不能用现有任务表直接回答“所有任务里多少比例用了赠送额度”，更不能把调用次数比例当成节省的 token 比例。

截至上述日期，可核验的 WorkBuddy **合成批次测试为 3 次**：2 次手动 CLI 测试，1 次通过本地 Subagent API 执行并验收。它们不是 3 个真实业务批次，也不覆盖连通探针的全部调用历史。统一链路的 8 条测试结果和原生用量见 [验证记录](login-delegation-validation.md)。

下一阶段拟以“一次独立、可验收的任务批次”为单位登记，避免按聊天消息数、反馈条数或重试次数扩充分母：

| 拟记录内容 | 用途 |
|---|---|
| 批次 ID、任务类型、业务 / 合成测试标记 | 同一批次只计一次；业务与测试分开 |
| 首次选择：主代理 / 本地脚本 / 下游，以及理由 | 覆盖全部分级决定，包括没有外派的工作 |
| 实际尝试、执行器、结果、最终交付方式 | 记录失败及回退；重试归属原批次 |
| 验收结论、等待与执行时长 | 区分成功返回、合格交付与用户等待 |
| 主代理和下游分别报告的用量、单位、来源 | 缺失保持未知；探针另列，不计业务分流 |

拟展示的口径：

- **下游尝试占比**：同一统计范围内，至少实际调用过一次下游的业务批次 / 已登记的全部业务批次。后续回退主代理，仍只计一个曾外派批次。
- **下游合格交付占比**：通过下游结果验收、并以该结果交付的业务批次 / 同一范围已登记的全部业务批次。主代理重做交付不计入分子。
- **下游验收通过率**：已有最终验收结论的下游批次中，通过的比例；等待、执行失败、取消另列。报告分子、分母和样本范围。

这些是待实现的统计定义，**当前没有对应的汇总接口或看板，也没有完整登记覆盖率**。上线后仍应显示已登记范围和未完成批次；只登记下游仍无法获得可信的整体比例。

## 次数、积分和节省分开看

赠送积分、订阅额度、token、美元各有不同单位。平台返回费用为 0、额度未知，均不能解释成没有消耗。剩余积分未知也不能当作零或无限；积分的具体来源需要账号侧证据。

先报告可核验的调用次数、合格交付和各平台原生用量。若要测“省了多少”，需要同一组任务和相同验收标准的主代理直做基线，计入打包、下游失败 / 重试、主代理验收 / 返工的消耗。缺少基线或主代理用量时，节省比例保持未知；不直接把不同平台 token / credit 加成一个成本数。

## 多个 CLI 如何选择（待实现）

采用一条可解释的顺序，不先引入复杂评分模型：

1. **筛选可用执行器。** 已安装、正常授权、连通验证通过，且适合任务和数据边界。网页登录确认或宣传赠送积分不足以证明可调用。
2. **满足交付要求。** 使用相同任务类型的验收记录评估质量和等待时间；赶时间或复杂任务直接留给主代理。
3. **再比较额度和消耗。** 在质量可接受的候选中，可优先使用即将到期的赠送积分或已有闲置额度，再结合额外付费、等待和返工成本。余额与到期时间需要来源及更新时间。
4. **记录选择理由。** 随样本增长再调整顺序；没有数据就不宣称某平台“最佳”。执行器选择与平台内部模型选择是两层，当前 WorkBuddy 的实际模型由平台自动选择。

当前这条顺序只能选到 WorkBuddy。没有固定的“TeleAgent 优先于 WorkBuddy”规则，也没有已实现的跨 CLI 优先级配置。API 字段仍以 [任务契约](task-contract.md) 为准，不向现有请求添加尚不支持的 `provider`、`model`、`max_cost` 或 `max_retries`。

## 失败时怎么收尾

| 情况 | 当前主代理 / skill 的处理 | 多执行器阶段的方向 |
|---|---|---|
| 明确登录失效、额度不足或执行失败 | 停止该下游，说明原因，由主代理承接授权范围内的工作 | 可选其他已验证、符合约束的执行器 |
| 提交超时、没有 ID、不确定是否已经执行 | 先查最近任务及状态；无法确认时保留待核查，不盲目重发 | 跨平台切换前也必须排除仍在执行的重复任务 |
| 结果未通过验收 | 最多一次定向修正；仍失败则主代理收尾 | 整批共享尝试上限，换平台不重置计数 |
| 所有候选不可用或总消耗不值得 | 主代理或适用的本地脚本处理 | 保持同一兜底出口 |

“最多一次定向修正”是 skill 的执行约定，服务尚未实现跨任务的统一限次；具体跨平台预算和限次参数留待实现时确定。当前服务不会自动重试、自动回退或自动调用收费 API。任何将来增加的收费路径都应遵守用户的预算和授权范围。

相同请求重复提交会创建不同任务，当前没有幂等键。`GET /api/subagents` 仅返回最近 50 条；有 ID 时优先查询详情，无匹配结果不能单独证明请求从未执行。已完成的输出先验收复用，避免再次消耗。

## 第二个平台候选：TeleAgent

按名称及积分语境，候选为中国电信星辰超级智能体 [TeleAgent](https://www.teleai.com.cn/product/TeleAgent)。官方[权益中心说明](https://www.teleai.com.cn/doc/OJl4lKvRuPAOqMkuNesD/vXKMAeolsmc2bcaLf5Lt)介绍积分余额、来源、使用及到期信息；[套餐与积分说明](https://www.teleai.com.cn/doc/RJW5yep7xkz2PZZAJfRb/L2DkfOd2yLzDoV2tvsZU)介绍运营活动获取免费积分的方式。这些不代表已知某个用户的余额或赠送金额。

**TeleAgent 目前仅为研究候选，未加入工作台平台目录，未验证可外部调用的 CLI / headless 入口。** 产品能执行命令行工具，不等于产品本身提供外部 CLI。后续先核实正常客户端授权下的执行入口、结果获取与原生用量，再用同组合成任务验收，成功后才加入可派发名单。

实施顺序：**先补全分级登记和次数统计 → 验证第二个平台 → 加入可解释的优先顺序与有上限的回退 → 用真实质量和消耗调整策略。** 本次只更新说明与 skill，不启动这些功能的实现。
