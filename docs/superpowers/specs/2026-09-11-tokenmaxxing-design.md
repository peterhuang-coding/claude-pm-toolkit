# Tokenmaxxing 工作台：产品设计与首个平台实验

日期：2026-09-11。状态：产品方向已由当前对话确认；本文供本次计划评审。尚未实现执行器或批量实验。

更新：用户随后明确先测 WorkBuddy 桌面执行，再安装任务分级 skill；本文的 API 首测安排延期。当前不执行 GLM 接入或新增服务。

验证更新：WorkBuddy 随应用附带的 headless CLI 已完成 8 条反馈分类与文件验收，安装到 task-tiering skill 的脚本也实跑通过。当前交付是技能与命令行执行入口；本文后续工作台和服务 adapter 尚未实现。

## 1. 产品目标

Codex 负责理解需求、分解任务、处理困难判断和最终交付。下游处理范围明确、容易验收的小任务，优先使用已经购买而尚未使用的能力。

衡量单位是「一个验收合格的任务」，同时记录主力模型消耗、外部增量费用、订阅容量、返工和耗时。不同平台的请求数、积分、token、时间窗口分别保存，不换算成虚构的统一余额。

用户界面采用 HTML；操作提供 CLI。网页和 CLI 共用业务逻辑与任务记录。

## 2. 方案选择

| 方案 | 收益 | 代价 | 决策 |
|---|---|---|---|
| 只配 Codex 原生轻量 agent | 接入快，可作为对照 | 容量仍归属相应 Codex 额度池 | 保留为基线 |
| 单平台 CLI 实验，再接现有 Task Router 工作台 | 最快取得外部下游的质量、费用和失败证据 | 需要一个小型执行器与验收器 | 本次选择 |
| 一次完成多平台控制面与自动调度 | 覆盖范围广 | 在下游可用性和收益未知时投入过大 | 排在实验之后 |

## 3. 复用关系

- `toolkits`：复用 FastAPI、SQLite、Task/Attempt/Event/Artifact/Evaluation、路由解释和现有 CLI。工作台沿用 3459。
- `llm-hub`：复用平台登记和 Keychain 凭证引用。健康和预算字段必须说明来源及采集时间。
- `skill-hub`：保留现有技能管理职责。
- `claude-pm-hub`：提供后续经筛选的任务样本与决策记录。
- CCR、PM Provider Router、OpenClaw 继续服务原有调用方。首个实验直接访问选定平台，避免多层代理的重试与模型切换干扰测量。
- 首次实验是一次性 CLI，生成 JSON 和 HTML 报告；不增加常驻服务。

## 4. 首个平台：sfkey-glm

选择理由：本地已有凭证引用，登记模型为 `glm-5.2`，本地 tier 为 `plan`。这是待验证的订阅配置，尚不能据此认定剩余额度或增量费用为零。

2026-09-11 00:34 左右实测：

1. 现有配置地址已经是 `https://api.sfkey.cn/v1/chat/completions`。
2. `llm-hub/health.py` 再追加 `/chat/completions`，可形成错误路径，解释健康检查中的 404。
3. 本轮直接向配置中的完整地址发出一条无项目资料的分类请求，返回 HTTP 401、`new_api_error`、`Invalid token`，耗时 2858 ms；未获得模型输出和 usage。
4. 没有改 Keychain、平台配置或运行中的服务。有效凭证及权益确认是批量实验前置条件。

先解决凭证后再验证模型 ID；不根据一次认证失败推断模型是否存在。首个平台失败时停止并留下原因，不自动切换到付费下游。

## 5. 实验范围

先测一类任务：从短项目记录中提取「当前负责人、明确截止日期、当前状态」。它包含负责人变更、取消、完成、缺失信息等语义判断，同时容易建立人工标准答案。

- 首轮 10 条合成样本，不发送项目私有材料。
- 接通后先跑 1 条，再跑 10 条；质量达标后对这 10 条各跑 3 次检查稳定性。30 次调用仍然只有 10 个独立样本。
- 每条只发送任务说明和自身输入，不发送标准答案、对话历史、全量技能或整个项目目录。
- 并发 1；每次最多 512 个生成 token；超时 30 秒；单次命令最多 30 次请求；无隐藏自动重试。
- 记录平台返回的输入/输出 usage 数值、请求模型、返回模型、结束原因、时延、HTTP 状态、验收结果；凭证与请求头不落盘。
- 缺失 usage/价格/权益余额时显示 unknown，不记成零，也不承诺具体节省金额。

实施阶段按 1 + 10 + 30 的顺序累计最多 41 次请求；每阶段通过后才进入下一阶段。上限按请求和生成 token 控制，不假设已知订阅余额。

确定性排序、统计、格式转换由本地工具直接做，不为了消耗闲置额度而调用模型。

## 6. 通过门槛

| 阶段 | 通过条件 | 未通过 |
|---|---|---|
| 连接 | 正确地址、有效认证、非空模型输出；确认实际订阅适用范围 | 停在平台接入 |
| 功能 | 10 条首次输出至少 9 条与标准答案一致，所有失败均被标记 | 修订任务范围或模型参数，不自动放开 |
| 稳定性 | 30 次中至少 27 次通过，超时/认证/额度错误清楚可见 | 保持手动实验 |
| 收益 | 在同一批样本和同一验收口径下，与主力直接执行作对照；主力实际消耗目标降低至少 30%，全链路返工和外部费用在记录中可见 | 不宣称省 token，不扩大默认路由 |

30% 是建议的产品验收目标，尚无实测支持。若当前宿主不能导出任务级主力 token，则该指标记为未测；输入/输出字符数仅作代理指标，不换算成 Codex 订阅百分比。

## 7. 工作台与 CLI 的最小正式版本

实验通过后再把执行器接到现有 3459 服务。工作台先做一个页面，包含三块：

1. 平台容量：凭证存在、最近连接结果、模型、额度原始单位/重置时间/来源、可接任务。
2. 任务列表：目标、路由原因、执行器、阶段、验收、时延、增量费用；可停止、重试、交回 Codex。
3. 实验结果：通过率、主力消耗、外部 usage、返工率、费用未知项；详情展示精简结果与证据位置。

CLI 产品接口拟定为：

```text
taskctl providers --json
taskctl doctor --provider sfkey-glm --json
taskctl submit --input note.json --kind note-extract --policy economical --json
taskctl show TASK_ID --json
taskctl cancel TASK_ID --json
taskctl report --experiment EXPERIMENT_ID --json
```

以上新增命令是设计接口，当前仓库尚未实现。保留已有 templates/create/list/show/reroute 命令的兼容性。

所有写操作进入同一业务服务；网页不执行任意 shell，也不在浏览器存凭证。前端显示业务状态，不要求用户理解 ContextPack/Harness 等内部对象。

## 8. 路由规则

先过滤任务类型、数据可发送范围、验收能力、执行器是否实现、健康时效、容量和截止时间。

对满足条件的候选按以下顺序选择：

1. 确定性工具可以完整完成任务时直接执行。
2. 有历史通过证据的订阅能力，优先利用确实会到期/重置的闲置容量；保留必要容量，避免耗尽重要工作所需的额度。
3. 在已设置费用上限内选择低价按量能力。
4. 不适合下放或验收失败的任务交回 Codex。

首个平台实验固定执行器，暂不测试多平台自动评分。后续策略以任务类型的实测通过率更新，避免用预设质量分冒充能力证据。

模型失败后最多允许一次有明确原因的重试；认证失败不重试，额度失败等待或交回，结果验收失败先交回。重启时遇到结果不确定的远端请求，标记 interrupted，不静默重发并重复消费容量。

## 9. 后续扩展

单平台收益达标后选择第二个平台，以验证同一任务协议的可迁移性。WorkBuddy、用户提到的 Teleagent 都先核实具体产品、实际执行入口、认证方式、剩余额度和计量单位；有可用 CLI/API 才形成相应适配器。

正式执行器上线先采用显式实验任务标记和独立测试数据目录；不会让当前历史队列因新增 runner 而自动开始执行。多平台和后台长期调度各自另写实施计划。
